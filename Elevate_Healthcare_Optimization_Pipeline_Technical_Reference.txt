1. EXECUTIVE SUMMARY
================================================================================

This repo answers one main planning question:

  "If Elevate hires new field technicians, how many should it hire and where
   should they be based?"

The current live optimization flow is:

  Step 06 -> Step 11 -> Step 08 -> Step 09 -> Step 05

In simple terms:

  - Step 06 builds the clean optimization input tables.
  - Step 11 prices travel for every usable base-to-demand pairing.
  - Step 08 solves the hiring and assignment math problem.
  - Step 09 converts the raw solver output into annual business results and
    adds the patient-simulator install-upside view.
  - Step 05 loads those saved results into the interactive map.

  - 82 candidate bases
  - 110 demand nodes
  - 759 days of history

2. MAIN BUSINESS QUESTION
================================================================================

The model treats the service demand as fixed and asks:

  (a) Can the current team cover the work?
  (b) If Elevate hires 1 to 4 new technicians, where should they sit?
  (c) How does that change annual travel cost?
  (d) How much existing-tech load gets freed up?
  (e) What extra patient-sim install capacity could that freed time support?

The optimizer itself is cost-first.

That means Step 08 tries to minimize:

  - travel cost
  - time-zone / operational-zone penalties
  - hire payroll
  - optional out-of-region penalty
  - unmet-demand penalty

The install-upside analysis comes later in Step 09.

That matters because:

  - revenue does not change the Step 08 solve
  - the hire recommendation is still chosen from the cost-first results
  - Step 09 is a second business lens layered on top of the cost result

8.3  THREE-TIER TRIP LOGIC
--------------------------------------------------------------------------------

Step 11 uses three distance bands:

  1. drive_day
  2. drive_overnight
  3. fly

Current thresholds:

  - under 100 miles: drive_day
  - 100 to under 300 miles: drive_overnight
  - 300 miles or more: fly

--------------------------------------------------------------------------------
8.4  GROUND-TRANSPORT RULE
--------------------------------------------------------------------------------

Drive trips use one extra rule:

  - below 125 one-way median miles: personal-vehicle mileage
  - at 125 or above: rental-car economics

That means:

  - short drive trips use mileage reimbursement
  - longer drive trips switch to rental-day logic

Rental days are based on:

  trip_span_days = max(1, ceil(node_avg_days))

So rental cost grows with the modeled trip span.

--------------------------------------------------------------------------------
8.5  CURRENT COST CONSTANTS
--------------------------------------------------------------------------------

These come from scripts/config.py:

  - IRS mileage rate: $0.60 per mile
  - rental car: $40 per day
  - hotel: $165 per night
  - BTS national fallback fare: $386
  - corporate travel premium: 1.6x
  - personal-vehicle cutoff: 125 one-way miles

Important note:

  - older write-ups that mention $0.70 mileage, flat $235 rental, or $159
    hotel are stale
  - the current live code uses the values above

--------------------------------------------------------------------------------
8.6  HOW EACH TRIP TYPE IS PRICED
--------------------------------------------------------------------------------

Same-day drive:

  cost = mileage only

Overnight drive:

  cost = mileage or rental + 1 hotel night

Fly:

  cost = origin-airport BTS fare x 1.6
       + rental days
       + hotel nights

Important simplification:

  - flight cost is origin-only
  - it depends on the origin airport, not the exact destination airport

Their effective travel unit cost is:

  employee_style_unit_cost x 0.65 + 125

Then it is capped at:

This keeps contractors flexible, but not free.

9. STEP 08: SOLVE HIRING SCENARIOS
================================================================================

Script:
  scripts/08_optimize_locations.py

This is the actual hiring optimizer.

It uses SciPy's HiGHS-backed MILP solver. In plain English, that means it uses
a math optimizer that searches for the lowest-cost answer while obeying a set
of hard rules.

--------------------------------------------------------------------------------
9.1  CURRENT SCENARIO RANGE
--------------------------------------------------------------------------------

The saved run solves:

  N = 0, 1, 2, 3, 4

--------------------------------------------------------------------------------
9.2  DEMAND NODES
--------------------------------------------------------------------------------

Step 08 groups raw appointments into 110 nodes using:

  - state
  - skill class

Each node stores:

  - appointment count
  - total demand hours
  - average hours per appointment
  - plurality operational zone for that node

--------------------------------------------------------------------------------
9.3  DECISION VARIABLES
--------------------------------------------------------------------------------

Step 08 creates four kinds of variables:

  x = existing-tech assignments
  z = new-hire assignments
  y = number of hires placed at each candidate base
  u = unmet appointments

In simple terms:

  - x and z decide who covers the work
  - y decides where new hires sit
  - u is a last-resort safety valve if the model cannot cover something

--------------------------------------------------------------------------------
9.4  OBJECTIVE
--------------------------------------------------------------------------------

The model minimizes:

  travel cost
  + out-of-region penalty
  + time-zone / operational-zone penalty
  + hire cost
  + unmet-demand penalty

Current defaults:

  - out-of-region penalty: $0
  - unmet-demand penalty: $5,000 per appointment
  - annual hire cost: $146,640 per new hire

Important note:

  - the out-of-region penalty is still part of the objective shape
  - but in the current saved run it is effectively off because it is set to 0

--------------------------------------------------------------------------------
9.5  CAPACITY / LOAD MODEL
--------------------------------------------------------------------------------

The current model does not assume a fixed 2,080-hour year.

Instead it normalizes capacity against the current appointment-duration demand
pool.

Current saved values:

  - total demand hours: 85,578
  - total effective FTE: 11.55
  - target utilization: 0.85
  - hours_per_capacity_unit: 8,716.883

So:

  - each existing tech gets availability_fte x 8,716.883 capacity hours
  - each new hire gets 8,716.883 capacity hours

Important interpretation:

  - duration_hours is calendar-window workload
  - capacity_hours is normalized model capacity
  - utilization outputs are modeled load ratios

They are NOT:

  - literal payroll utilization
  - literal weekday labor utilization
  - literal clocked timesheet utilization

--------------------------------------------------------------------------------
9.6  HARD ELIGIBILITY RULES
--------------------------------------------------------------------------------

Current hard rules in live code:

  - HPS work can only go to HPS-certified existing techs
  - Learning Space work can only go to LS-certified techs

--------------------------------------------------------------------------------
9.7  OPERATIONAL-ZONE RULES
--------------------------------------------------------------------------------

The current model uses broad airport-based operational zones:

  - Eastern

Important Arizona handling:

Current standard employee / new-hire rule:

Current contractor rule:

9.10  CURRENT RECOMMENDATION RULE
--------------------------------------------------------------------------------

The analysis layer uses:

  proven_optimal_only

Meaning:

  - if at least one scenario is proven optimal, pick the best scenario from

  - if none are proven optimal, then fall back to the lowest observed cost

That is why:

  - N=0 has the lowest observed annual cost
  - N=1 is still the current official recommendation in the repo

10.1  WHAT STEP 09 DOES
--------------------------------------------------------------------------------

  - measures how much existing-tech load is freed
  - converts that freed load into patient-sim install capacity

--------------------------------------------------------------------------------
10.2  CURRENT ANNUALIZATION RULE
--------------------------------------------------------------------------------

Step 09 divides the period-total cost columns by:

  data_span_years = 2.078

That is why the map and reports show annual values rather than raw full-period
totals.

--------------------------------------------------------------------------------
10.3  CURRENT FREED-CAPACITY MATH
--------------------------------------------------------------------------------

The current install-capacity math is:

  1. Compare existing-tech assigned hours at N=0 vs each hire scenario
  2. Treat the difference as freed existing-tech hours
  3. Convert hours to calendar days by dividing by 24
  4. Keep only 30% of that time as realistically usable
  5. Divide by weighted-average install calendar days

Current key assumptions:

  - freed-capacity utilization factor: 0.30
  - capacity time unit: calendar_days
  - weighted-average install calendar days: 1.517857
  - weighted-average install revenue: $47,276.79
  - weighted-average install profit per install: $18,910.71

Important meaning of the 30% factor:

  - the code assumes only part of the freed calendar time becomes actual new
    installs in the real world
  - this is meant to absorb scheduling friction, admin work, sales-pipeline
    limits, and other real-world loss

--------------------------------------------------------------------------------
10.4  CURRENT INSTALL MODEL
--------------------------------------------------------------------------------

The current Step 09 model is not the old low / mid / high install bucket model.

It is now a family-based patient-sim install-only model that:

  - rebuilds install history from the raw workbook first
  - parses product-family signals from Description and Subject
  - excludes AVS / Learning Space from patient-sim revenue
  - excludes obvious non-net-new install rows
  - separates historical mix from forward mix
  - excludes HPS from the forward mix by default
  - uses per-family revenue, margin, and install-day assumptions

Current normalized families:

  - Apollo
  - Lucina
  - Juno
  - Ares
  - Aria
  - Evo
  - Luna

11.4  CURRENT TERRITORY DOT LOGIC
--------------------------------------------------------------------------------

The colored assignment dots on the map are not direct raw solver outputs.

Why:

  - the solver assigns work at the node level
  - the map wants to show actual appointment points

So Step 05 rebuilds appointment-level ownership like this:

  1. take the node-level assignment quotas from Step 08 outputs
  2. round them to whole appointments
  3. fix any rounding mismatch by adjusting the biggest quota
  4. assign individual appointments to assignees using a nearest-base greedy
     rule

Important meaning:

  - the dots are a visualization reconstruction
  - they are meant to tell the story of coverage
  - they are not a separate new optimization solve

15. MAIN LIMITS AND SIMPLIFICATIONS
================================================================================

These are the main things to keep in mind when using the current model:

15.1  DURATION_HOURS IS NOT HANDS-ON LABOR
     -------------------------------------------------------------------------

  - the model uses appointment duration as calendar-window workload
  - that is practical for this dataset
  - but it is not the same thing as direct labor time

15.2  FLIGHT COST IS ORIGIN-ONLY
     -------------------------------------------------------------------------

  - the flight component depends on the origin airport
  - it does not vary by exact destination airport

15.3  DEMAND IS AGGREGATED TO NODES
     -------------------------------------------------------------------------

  - Step 08 solves on state + skill nodes
  - it does not optimize each appointment as its own separate variable

15.4  MAP DOTS ARE A VISUAL RECONSTRUCTION
     -------------------------------------------------------------------------

  - the map rebuilds appointment-level ownership from node quotas
  - that is useful for storytelling
  - but it is not a second exact optimization

15.5  FAMILY ECONOMICS ARE STILL PLANNING ASSUMPTIONS
     -------------------------------------------------------------------------

  - per-family install revenue values are provisional
  - the code is ready for those values to be replaced later

15.6  HPS IS EXCLUDED FROM THE FORWARD MIX
     -------------------------------------------------------------------------

  - HPS remains in historical reporting
  - HPS is excluded from the forward-looking install upside by config

15.7  CANADA IS VISIBLE ON THE MAP BUT OUT OF OPTIMIZATION SCOPE
     -------------------------------------------------------------------------

  - Canada still appears in some map-side data and territory layers
  - Canada is filtered out of Step 06 demand before optimization

15.8  ANCHOR MODELING IS SIMPLE BY DESIGN
     -------------------------------------------------------------------------

  - the current anchor logic reduces available FTE and limits scope
  - it does not create synthetic anchored demand rows
  - that simpler approach is intentional in the current code

18. GLOSSARY
================================================================================

Annualized
  Taking a multi-year total and converting it to a per-year number.

Candidate base
  A possible city or airport where a new hire could be placed.

Demand node
  A grouped bucket of appointments defined by state + skill class.

Effective FTE
  The amount of field capacity left after applying availability overrides.

Full cost table
  The precomputed travel-cost table for each origin-to-node pairing.

Install units enabled
  The model's estimate of how many patient-sim installs the freed capacity
  could support.

Modeled load ratio
  The current repo's better interpretation of the legacy utilization fields.
  It means assigned modeled workload divided by modeled capacity.

Operational zone
  A broad airport-based bucket like Eastern or Central used to add assignment
  realism without building a minute-by-minute scheduling engine.

Proven optimal
  The solver has mathematically proven that no better answer exists within the
  current model setup.

Stakeholder mode
  The cleaner default map mode that emphasizes the business story over heavy
  debug layers.
